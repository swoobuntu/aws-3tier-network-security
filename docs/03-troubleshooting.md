## 1. WAF가 반려동물 사진 업로드를 전부 막음

| 항목 | 내용 |
|---|---|
| 상황 | WAF를 Public ALB에 연결하자 반려동물 사진 업로드(`POST /petclinic/owners/{id}/photo`)가 동작하지 않았다 |
| 어려웠던 점 | 같은 시기 로그에 실제 공격성 요청(`.env`, PHP 취약점 스캔 경로 등)의 차단도 섞여 있어, 정상 차단과 오탐을 구분해야 했다 |
| 조사 | WAF 로그 24시간분을 "어느 규칙이 어떤 요청을 막았는지"로 분류했다 |
| 원인 | 차단된 업로드 요청의 본문은 약 80KB(multipart). 관리형 Common 규칙의 본문 크기 제한(`SizeRestrictions_BODY`)은 8KB 초과를 차단한다 → **정상 업로드가 걸린 오탐** |
| 1차 조치 | 규칙 그룹 전체를 끄지 않고 **문제가 된 하위 규칙 하나만 Count로 전환**해 업로드 기능을 복구했다 |

**로그 분류 결과**

| 분류 | 걸린 규칙 | 판단 |
|---|---|---|
| 정상 기능 차단 | Common · 본문 크기 제한 | **오탐 — 수정** |
| 부하테스트 트래픽 | Rate 제한 | 부하테스트 IP 예외 등록 |
| 헬스체크 등 User-Agent 없는 요청 | Common · User-Agent 검사 | 필요 시 예외 |
| SQL 인젝션 시도 | SQL Injection | 정상 방어 — 유지 |

**한 단계 더 — 1차 조치의 문제를 짚음**

하위 규칙을 Count로 돌리면 업로드뿐 아니라 로그인 · 검색 같은 **모든 경로의 본문 크기 제한이 함께 사라집니다.**
그래서 "업로드 경로만 예외로 둘 수는 없는가"를 다시 조사했습니다.

- Count로 바꿔도 WAF는 요청에 "크기 초과" **라벨**을 계속 붙입니다.
- 뒤 순위에 "이 라벨이 있고, 경로가 업로드(`/photo`)로 끝나지 않으면 차단" 규칙을 두면 업로드 경로만 예외가 됩니다.
- 크기 판단을 다시 구현하지 않고 관리형 규칙의 판정 결과를 재사용하는 방식입니다.

> 이 경로 단위 예외 규칙은 설계까지 정리했고, 프로젝트 기간 안에 실제로 적용했는지는 기록으로 확인하지 못했습니다.

**배운 점**
- 관리형 규칙은 바로 Block하지 말고 Count로 관찰한 뒤 전환한다.
- 예외는 규칙 단위로 넓게 끄지 말고 **경로 단위로 좁힌다.**
- 보안 규칙과 부하테스트는 충돌한다. 예외 대역을 관리 대상으로 둔다.

## 2. MFA 강제 정책 때문에 팀원이 로그인 후 막힘

| 항목 | 내용 |
|---|---|
| 상황 | 팀원용 IAM 사용자를 만들면서 "첫 로그인 시 비밀번호 변경"과 MFA 강제 정책을 함께 적용했다 |
| 증상 | 팀원이 초기 비밀번호로 로그인한 뒤 비밀번호 변경이 거부(Deny)되어 콘솔을 쓸 수 없었다 |
| 원인 | MFA 강제 정책은 `Effect: Deny` + `NotAction: [허용 목록]` 구조다. MFA 등록 전에는 목록 밖의 모든 작업을 막는데, 목록에 `iam:ChangePassword`가 빠져 있었다 |
| 조치 | `NotAction` 목록에 `iam:ChangePassword`를 추가했다 |
| 배운 점 | `Deny + NotAction` 패턴은 "허용 목록 바깥을 전부 차단"한다. 계정 초기 흐름(비밀번호 변경, MFA 등록)에 필요한 작업을 빠짐없이 넣어야 한다 |

## 3. S3 Gateway 엔드포인트를 쓰는데 NACL에서 멈춤

| 항목 | 내용 |
|---|---|
| 상황 | NAT 없이 WAS가 S3에 업로드 · 다운로드하고 Amazon Linux 저장소에도 접근해야 했다 |
| 증상 | NACL을 사설 대역 위주로 잠그자 S3 접근이 응답 없이 멈췄다 |
| 원인 | 게이트웨이 엔드포인트를 지나도 인스턴스가 접근하는 주소는 S3의 **공인 IP**다. 보안그룹은 프리픽스 리스트를 참조할 수 있지만 **NACL은 참조할 수 없다** |
| 조치 | NACL 아웃바운드에 S3 대상 443을 허용하고, PRIVATE-RT에 S3 프리픽스 리스트 → 게이트웨이 엔드포인트 경로가 있는지 확인했다 |
| 추가 확인 | 게이트웨이 엔드포인트는 **같은 리전** S3만 지원한다. AI 도구가 처음 내놓은 설명이 틀렸다는 것을 공식 문서로 다시 확인했다 |
| 배운 점 | "주소는 공인 IP, 경로는 사설망." NACL과 보안그룹이 참조할 수 있는 대상이 다르다 |

## 4. Flow Logs가 켜져 있는데 로그가 0바이트

| 항목 | 내용 |
|---|---|
| 증상 | VPC Flow Logs 상태는 ACTIVE였지만 전달 상태가 `Access error`였고, 로그 그룹 저장량이 0바이트였다 |
| 원인 | Flow Logs용 IAM 역할의 신뢰 정책 Principal이 `ec2.amazonaws.com`으로 잘못 들어가 있었다. 올바른 값은 `vpc-flow-logs.amazonaws.com`이다. 권한 정책(CloudWatch Logs 쓰기)은 문제가 없었다 |
| 조치 | 신뢰 정책의 Principal을 수정했다 |
| 배운 점 | **"켜져 있다"와 "실제로 기록되고 있다"는 다르다.** 이후로는 리소스를 만든 뒤 상태 표시가 아니라 실제 산출물(로그 · 지표)이 생기는지까지 확인한다 |
